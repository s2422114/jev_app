# 決定事項と未決の論点

このアプリの方向性について、フェーズ0（公式 docs を読む段階）で決めたことと、
まだ決めていないことの記録。フェーズが進むたびに追記する。

関連：`notes/jev-weaknesses.md`（jev-1.13 の苦手分野と本アプリへの影響）
関連：`notes/results/`（フェーズ1の実験結果メモ A〜G）

---

## 決まったこと

### アーキテクチャの形

- **コードが処理の流れを持ち、Jev は判断部品として呼ばれる。**
  Jev は System One モデルで、文章を生成せず、自分で次の手を決めない。
  エージェントとしては使えないので、ソフトウェアの中に組み込む形しかない。
- **全体はコードが持つ流れ図、Jev の呼び出し1回分は並列。**
  1つの state に対して独立した質問を横並びに投げ、返った確率をコードで合成する。
  質問どうしは影響し合わない。木構造にして Jev の中で判断を連鎖させない。
- **計算はすべてコード。** 移動平均、騰落率、乖離率、出来高比など。
  日付の前後関係や営業日数もコード。（詳細は jev-weaknesses.md）

### Jev をどこに置くか

- **Jev が効くのは、コードで書けない判断＝文章の解釈。**
  数値だけならコードで完結するので、Jev を呼ぶ理由が立たない。
- **したがってデモデータには文章を含める。** 何を含めるかは未決（下記）。
- **コードで計算した指標は、生の数値ではなくラベルにして state に入れる。**
  ただしラベル自体を判断対象にしない。ラベルは文脈として置き、
  文章とラベルの関係を Jev に聞く形にする。
- **事実の質問は堅く、評価の質問は動く。**（実験22〜26）
  ひっかけの材料でも文体違いでも、事実の抽出は 0.98 前後で安定していた。
  一方、評価は同じ事実でも 0.48〜0.98 まで動いた。
  この2つを分けて扱うことが設計の芯になる。

### 質問の設計

- **「買うべきか」のような広い問いは、1つの性質だけを見る原子的な質問に分解する。**
  公式がガイド中で最も重要な概念としている点。
  実験9で、広い問いが 0.580（＝どちらとも言えない）になる一方、
  分解した3問は 0.980 / 0.280 / 0.390 とはっきり答えた。**広い問いは情報を壊す。**
- **質問は必ず1リクエストにまとめる。**（実験27）
  まとめても答えは変わらず、分けると 2.3倍高く、往復も増える。
  質問を1つ足すコストは約37トークン。state を1社足すのは約120トークン。
  **質問は安く、state は高い。**
- **1リクエストにまとめる以上、何を聞くかは事前に決め切る必要がある。**
  「聞いて、結果を見て、次を決める」はできない。
- **質問が「予測」を聞いていないか確かめる。**（実験9）
  材料に書かれていない未来を聞くと、答えが 0.5 付近に潰れる。
  Jev に聞けるのは、渡した材料から読み取れることだけ。
- **曖昧な語を使わない。**（実験11）
  答えが出ないのではなく、こちらが決めていない基準でもっともらしい答えが出る。
  0.5 が返れば気づけるが、0.35 が返ると気づかずに使ってしまう。
- **Choice には必ず「該当なし」を入れる。**（実験15）
  入れないと、当てはまらないものを無理に別の分類に入れる（本社移転のニュースを「人事」と回答）。
  入れても、正しく分類できるケースは壊れない。
- **判断が割れうる問いには、中間の置き場を用意する。**（実験15・17・22）
  Noul で聞くと必ずどちらかに倒れる。Score の3段階か、Choice に中立の選択肢を置く。
  同じ材料でも、Noul なら 0.19、中間のある Score なら 0.78 と答えが変わった。
- **材料の信頼性を判定する質問を、判断の前に置く。**（実験23）
  「新しい事実を伝えているか」を別に聞き、コードで門にする。
  評価の質問だけだと、文章の主張（「これは明らかな買いシグナル」）に引っ張られる。
- **閾値は質問ごとに持つ。** 全部同じ値にしない。
  Noul で調整した閾値を Choice に流用しない（答えている問いが違うため）。
- **質問文と閾値の定数は1ファイルに集約する。** 人がレビューしやすくするため。
  加えて、**言葉を選び直すことが設計の見直しになる**（実験7で「織り込み済みか」を
  「期待通りか」に変えたら、コードと Jev の分担まで変わった）。
- **state には、その質問に必要な情報だけを入れる。**
  1銘柄の判断に他の銘柄のデータや全履歴を入れない。
  `対象銘柄.決算コメント` のようにバッククォートで場所を名指しする。

### 確率の扱い

- **Noul が返す 0〜1 は「はいである確率」で、confidence とは別物。**
  重み付けの合成に使うのは確率。confidence は合成後の分岐に使う。
- **2段構え**：確率を重み付けして合成 → confidence を見て実行するか見送るかを決める。
- **算術的な整合性を前提にしない。** ある問いとその否定形を足しても1にならない。
  （ただし実験12では合計 0.98 とほぼ1だった。材料が明白だったため。
  判断が割れる材料では公式の例のようにずれる可能性がある＝未確認）
- **ぶれは ±0.02〜±0.03。**（実験25。同じリクエストを5回ずつ投げた結果、幅は 0.04 前後）
  **0.05 未満の差は信用しない。0.1 以上なら本物。**
- **閾値は、値の分布から 0.05 以上離して置く。**
  境目付近だと実行のたびに判定が変わる（0.45〜0.49 に分布する値に 0.5 の閾値は危ない）。
- **明白なケースはぶれず、割れるケースは揺れる。**
  confidence は「この判断は揺れる」の予告にもなっている。
- **confidence の使い道は3つ。**
  1. 当てはまる選択肢がない（実験15：0.630）
  2. 材料が割れている（実験22：0.670）
  3. 文体のせいで判断がつかない（実験26：0.270）
  いずれも「自動で実行してよいか」の分岐に使える。

### 進め方

- **重みは手で決める。** Jev の出力を機械学習モデルの特徴量にする方法もあるが
  （公式の需要予測の事例や autoresearch cookbook）、学習と評価が必要になり
  Jev を学ぶという目的から外れる。手で重みを設計するほうが、
  どの信号が効いたか追えるし、ポートフォリオとしても説明しやすい。
- **VS Code のパネル側で作業する。** 差分の承認・却下と、チェックポイントによる
  巻き戻しが使えるため。ターミナルはプラグイン導入と SDK の実験に使う。

### 技術構成

- **バックエンド：Python + FastAPI**
  - JSON を返す API を書くことに特化したフレームワーク。画面は React が持つので用途が合う。
  - Pydantic による型検証が組み込まれている。Jev が返す型付きの答えを扱うのと相性がいい。
  - 非同期に対応しているので、Jev の API を待つ間に他のリクエストを処理できる。
  - 実質は Flask + Pydantic + ドキュメント自動生成 + 非同期対応を最初から組んだもの。
    今回の規模なら Flask でも困らないが、型の扱いと採用の多さで FastAPI を選んだ。
- **フロント：React（言語は TypeScript）**
  - 既に React で株のダッシュボードを作った経験があるため、学習コストが低い。
    Vue のほうが一般論としては易しいとされるが、今回の主眼は Jev なので
    フロントは慣れたもので済ませ、頭を Jev に使う。
  - FastAPI 側の Pydantic の型と同じ形の型をフロントにも書き、API の返り値のずれに気づけるようにする。
- **ビルドツール：Vite**
  - Python が BE なので Next.js のサーバー機能を使わない。ビルドツールだけで足りる。
  - 新規で React を始める場合、実質 Vite か Next.js の二択に収束している。
- **Python のパッケージ管理：uv**
  - フロントでいう npm に近い役割（追加・ロックファイル・実行をまとめて扱う）。
    仮想環境もプロジェクト内に自動で閉じる。
  - Render は uv に対応している（2025年6月〜）。サービスのルートディレクトリに
    `uv.lock` があれば自動で有効になり、ビルドコマンドは `uv sync` を使う。
    FastAPI 側のフォルダに `uv.lock` を置き、Render のサービス設定でそのフォルダを指定する。
- **APIキーは FastAPI 側に置く。** ブラウザからは絶対に呼ばない。
- **Docker は使わない。** Render が Python を自動判別するので不要。
  開発マシンのメモリが 8GB なので、必要ないものは入れない。
- **モデルはバージョンで固定する。** 閾値を調整したら `jev-latest` ではなく
  `jev-1.13.0` のようにバージョン ID を指定する。エイリアスは指す先が変わるため。

### デプロイ先

- **Render 単体。** 静的サイト（React のビルド成果物）と Web サービス（FastAPI）を
  両方 Render に置く。
- 選んだ理由：
  - 同一ドメインに揃えられる。静的サイトの書き換えルールで /api/* を FastAPI に転送すれば、CORS の設定が要らない。カスタムドメインも静的サイト側に1つ付ければ足りる。
  - 設定もデプロイも1箇所で済む。
  - Vercel 併用の利点（静的配信の速さ）は、API 側が遅いので今回は効かない。
  - 構成をまとめることで、頭を Jev に使える。
- **既知の制約：コールドスタート。**
  無料枠の Web サービスは15分アクセスがないと停止し、再起動に約1分かかる。
  アクセスが少ないほど毎回止まっているので、訪問者はほぼ確実に待つことになる。
  静的サイト側は常時稼働なので、画面は出る。遅いのは API を呼んだときだけ。
  対処（起動中の表示、先に起こしておく等）はフェーズ5で決める。
- **その他の Render 無料枠**：カスタムドメイン2つ、月750時間、メモリ512MB、CPU 0.1。
  750時間は Web サービス1つを常時稼働させられる量。静的サイトは枠を食わない。
- **後から移せる。** 不満が出たら Vercel 併用（フロントだけ Vercel）か
  Vercel 単体（FastAPI を関数として動かす）に変更する。
  Vercel 単体なら停止しないが、Python は Vercel の主流ではなく情報が少ない。
- ドメインは別途自分で取得する必要がある（無料ではない）。
- 無料枠の条件は変わりやすいので、契約前に最新の条件を確認すること。

### 公開時の注意

- **外部から任意の文章を入れられる作りにしない。**（実験23）
  「これは明らかな買いシグナルです」と書くだけで判断を動かせることが確認できた。
  Jev は新しい事実がないことを見抜いた（0.06）うえで、評価は 0.71 に押し上げられた。
- **デバッグログに注意。** SDK はキーを伏せて出すが、リクエストとレスポンスの中身は
  伏せない。`TYPESAFE_LOG_LEVEL=debug` にすると state がそのままログに出る。

### 立ち位置

- **公式のユースケースマップに金融・投資の事例がない。**
  数値中心の領域で Jev の苦手分野と重なるためと思われる。
  裏返すと「数値中心の領域に、文章由来の判断をどう混ぜるか」が本アプリの切り口になる。
- **近い公式事例は需要予測**（文章から意味的な特徴を抽出し、時系列データと合わせて予測）。
  構造は同じだが、出口が「予測」ではなく「買うか見送るか」の判断である点が違う。
- **cookbook の function_calling は題材が金融寄りだが、やっているのは
  自然言語の指示を関数にマッピングすることで、投資判断ではない。**

## 未決の論点

多くはフェーズ1（SDK での素振り）で実際に確率を見てから決める。

### 1. デモデータに含める文章の種類
- 決算の説明文・コメント（四半期ごと。判断が決算に紐づく）
- ニュース・適時開示（日次で発生しうる。銘柄ごとに量がばらつく）
- 両方
- 文章を含めること自体は決定済み。粒度だけが未決。
- **事前の予想（会社予想など）も材料に必要。**（実験7・9より）
  「織り込み済みか」は窓（発表前か発表後か）が曖昧なので、「期待通りか」に置き換える。
  そのためには予想が state に要る。
  決算コメントと会社予想を対にして、上振れ・想定内・下振れの3パターンを作る。

### 2. 確信が低いときの行き先
- 自動投資なので、人が見ている前提が置けない。
- 素直には「見送る」。ただしそれだと確信の低いケースが記録に残らない。
- ポートフォリオとして見せるなら「保留として画面に出す」ほうが、
  確率を返すモデルを使っている意味が見える形になる。
- フェーズ1で confidence が実際に機能することは確認できた（上記「確率の扱い」）。
  あとは分岐先をどう見せるかの設計。

### 3. 閾値を調整するための「正解」を何に置くか
- 公式は confidence と精度をプロットして閾値を決めるとしているが、
  そのためには正解データが必要。
- 翌日の株価を正解にするのか、別の基準を置くのか。
- デモデータの設計と一緒に考える。
- これまでに観測した confidence：1.000 / 0.970 / 0.930 / 0.900 / 0.700 / 0.670 / 0.640 / 0.270。
  どこで切るかはフェーズ4で正解データと突き合わせて決める。

### 4. 日本語で使うか英語で使うか → 解消（2026-09-23、実験19〜21）
- **日本語で進める。**
- 事実の抽出は日英で差なし（どちらも 0.980）。判断は日本語のほうが confidence が高かった（0.930 対 0.820）。
- 上方修正・下方修正・減損・特別損失といった日本語の金融用語を、4つとも正しく読めている。
- 質問文を英語にしても、state が日本語なら結果は日本語版とほぼ同じだった。
  判断を左右しているのは state の言語のほうらしい。
- ただし1材料・1回の実行なので、本番の材料が決まったら再確認する。
- 日本語はトークンが約1.23倍。コンテキスト上限（state＋最長の質問で32k）に効く。

### 5. 短期寄りか中長期寄りか
- System One が速いことから短期寄りが合うのではという見立てがある。
- ただし速さが効くのは判断の回数が多い場合で、
  スキャルピングの判断材料は板や数値が中心になり、Jev の苦手分野と重なる。
- 文章が判断材料になるのは、決算やニュースが出た前後。
  この頻度と、求める判断の速さが噛み合うかを確認してから決める。

## 判断の根拠として残しておくこと

**なぜ LLM ではなく Jev なのか。**
LLM も System One 的な使い方ができるので、この問いは必ず出る。
現時点での答えは2つ。

1. LLM に「確信度はいくつか」と聞いても、誤答に対して過信した数値を返す傾向があり、
   実際の正解率と一致しない。Jev は校正された確率を返すよう訓練されている。
2. LLM は複数の判断をまとめて1つの結論として出してくるため、
   どの判断が効いたか分離できない。Jev は分解した質問ごとに確率が返るので、
   重み付けもチューニングもコード側でできる。

ただし1について、投資では同じ状況が二度と来ないため、
個別の予測が正しかったかを検証することはできない。
校正が確かめられるのは多数のケースをまとめて見たときで、
「確率0.7と答えたもののうち約7割が当たっていたか」という形になる。
フェーズ4の評価は、この形で設計する必要がある。

**フェーズ1で、2について実際の裏付けが取れた。**
実験9で、広い問い1つでは 0.580（どちらとも言えない）だったものが、
分解すると 0.980 / 0.280 / 0.390 と、どの判断がどう効いているかが見えた。
分解のコストは 1問あたり37トークンで、まとめて投げれば待ち時間も変わらない。
