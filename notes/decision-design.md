# 判断の設計（フェーズ2）

このアプリが何を判断し、Jev とコードがどう分担するかの設計。
フェーズ1の実験結果（`notes/results/`、`notes/phase1-summary.md`）を踏まえて決めた。

関連：`notes/decisions.md`（方針全体）

---

## アプリの形

**市場全体を監視し、材料（ニュース・開示）が出た銘柄について、
翌日の売買リストに入れるかを判断する。**

フェーズ2の途中で、当初の「1銘柄を買うか」から形が変わった。経緯は下の「なぜこの形になったか」。

### 全体の流れ

| 担当 | 仕事 |
|---|---|
| コード | ニュース・開示を集める |
| **Jev** | **文章を読んで判断する（7問を1リクエストで）** |
| コード | 門を通し、確率を合成し、confidence で絞る |
| コード | チャート・出来高で弾く（下記「コード側の規律」） |
| コード | 翌日の売買リストを作る |
| LLM | そのリストを見て、仮想取引を執行する |

LLM が執行を担当するのは、一度やってみたいという理由。
ただしフェーズ3では、まずコードで執行する形で縦切りを通す。動いてから差し替える。
差し替えられる形にしておけば、コードの執行と LLM の執行を比べることもできる。

## Jev に聞くこと（7問、1リクエスト）

質問文（instructions / criteria）はまだ書いていない。state の形が決まってから詰める。

| キー | 何を聞くか | 型 | 使い方 |
|---|---|---|---|
| `new_info` | 新しい情報を含んでいるか（既報の焼き直しでないか） | Noul | 門 |
| `market_moving` | 業績に直結する種類の発表か | Noul | 門 |
| `official_announcement` | 企業が公式に発表した内容か | Noul | 門 |
| `direction` | 企業にとって良い材料か悪い材料か | Score（3段階） | 門 |
| `above_expectation` | 事前の予想に対して上振れているか | Score（3段階） | 和（0.40） |
| `magnitude` | 業績への影響が大きいか | Score（3段階） | 和（0.35） |
| `continuing` | その影響は続くものか | Noul | 和（0.25） |

### 型の選び方の根拠

- **Score を選んだもの**は、中間の答えがありうるため。
  実験15・17・22で「中間の置き場があれば使い、なければどちらかに倒れる」ことが分かった。
  `direction` は「どちらとも言えない」、`magnitude` は大中小、
  `above_expectation` は上振れ・想定内・下振れ。
- **Noul を選んだもの**は、はい・いいえで足りるもの。

### 向きを揃えてある

`continuing` は当初 `temporary`（一時的な要因か）だったが、
合成で反転（1 - temporary）が必要になるため質問ごと変えた。

実験12で肯定形と否定形の合計がほぼ1になったが、あれは判断が割れない材料でのこと。
割れる材料では未確認なので、**反転せずに済む書き方にした**。
これで4つとも「値が大きいほど買いに有利」に揃っている。

### 門を分けた理由

当初は `new_info` に「市場が反応しうる、新しい情報を含んでいるか」と2つの判断を入れていたが、
1問1判断の原則に反するので分けた。

分けたことで、**弾かれた理由が特定できる**。既報だったのか、内容が地味だったのか、
記者の意見だったのか。実験9で見た「分解すると、どの判断が効いたか見える」と同じ効き。

質問を足すコストは1問約37トークンなので、増やしても問題ない（実験9）。

### `market_moving` の質問文には注意が要る

「市場が反応しうるか」は、材料の中身ではなく**市場の反応の予測**を聞いている。
実験9で、予測を聞くと答えが 0.5 付近に潰れることが分かった。

質問文を書くときは、state から読み取れる材料の性質として書く。
（例：「投資家が売買の判断に使う内容か」のような形）

### `market_moving` の中身

**「業績に直結する種類の発表か」を聞く。**

当初は「市場が反応しうる内容か」だったが、これは**市場の反応の予測**を聞いている。
実験9で、予測を聞くと答えが 0.5 付近に潰れることが分かっている。
「株価に影響するか」も同じ理由で使わない。

**Jev が答えられるのは、渡した材料から読み取れることだけ。**
開示文を読めば、業績の話か周辺の話かは分かる。
「業績に直結するものは株価が動きやすい」という因果は、こちらが持つ。
（実験7で「織り込み済みか」を「期待通りか」に言い換えたのと同じ構造）

**質問文に「株価」が出てきたら疑う。**
state に株価の情報が入っていてそれを読むだけなら問題ないが、
「株価がどうなるか」を聞いているなら、それは予測。

**true に入るもの**：決算発表、業績の上方修正・下方修正、M&A・買収、業務提携、自社株買い
**false に入るもの**：本社移転、人事異動、既報の焼き直し、アナリストの分析記事

自社株買いは業績そのものではないが需給に効くため、true に入れると決めた。

**`magnitude` との切り分けは、いまは criteria に書いていない。**
本来は「影響の大きさは問わない。小さくても業績に関わる内容なら true」と書くべきだが、
まず書かずに動かし、小さい材料が弾かれるようなら足す。

**なお、金利・為替・経済指標・地政学リスクは市場全体に効くもので、
個別銘柄の材料ではない。** このアプリの判断の対象外。
扱うとしたら「今日は地合いが悪いので全体的に見送る」という別の層になる。

## 合成

### 先に：Score を 0〜1 に正規化する

**Noul は 0〜1、Score は 0〜2（3段階の期待値）を返す。スケールが違う。**

このまま重み付き和を計算すると、Noul の実効重みが半分になってしまう。
たとえば 0.40×above(0〜2) + 0.35×magnitude(0〜2) + 0.25×continuing(0〜1) だと、
満点が 1.75 で、`continuing` の実効的な重みは 0.25 ではなく 0.14 相当になる。

**Jev から受け取った直後に Score を2で割り、以降はすべて 0〜1 で扱う。**

```
above_expectation = response.scores["above_expectation"].score / 2
magnitude         = response.scores["magnitude"].score / 2
direction         = response.scores["direction"].score / 2
```

合成の式の中で割ると読みにくいので、受け取った直後に揃える。
これで門の閾値もすべて 0〜1 のスケールになり、スコアの満点も 1.0 になる。

### 流れ

```
Score を2で割って 0〜1 に正規化
  ↓
門：4つとも通らなければ見送り（閾値は質問ごとに別の変数。すべて 0〜1）
  new_info          >= 閾値A
  market_moving     >= 閾値B
  official_announcement >= 閾値C
  direction         >= 閾値D
  ↓
confidence：Score 3問（direction / above_expectation / magnitude）の
            1つでも低ければ見送り。Noul に confidence は返らない
  ↓
スコア = 0.40 × above_expectation
       + 0.35 × magnitude
       + 0.25 × continuing
       （すべて 0〜1。満点は 1.0）
  ↓
スコア >= 閾値E なら、翌日の売買リストに入れる
```

### direction を門にした理由

当初は和に入れていたが、**悪い材料を弾きたい**という意図に対して門のほうが合う。

和だと、`magnitude` と `above_expectation` が高ければ、
`direction` が低くても押し上げられて通ってしまう可能性がある。

### 重みの根拠（ユーザーの判断）

1. **`above_expectation` が最も重い（0.40）**
   株価は事前の期待と異なるインパクトがあるほうが上がりやすい。
2. **`magnitude` が次（0.35）**
   above とセットで「期待との差の大きさ」を作る。
3. **`continuing` が最も軽い（0.25）**
   短期寄りなので影響が続くかは相対的に重要度が低い。
   ただし1日で上昇が終わっては意味がないので、ある程度は要る。

**これは仮の値。** フェーズ4で正解データと突き合わせて調整する。

### confidence の見方

**まず「Score の1つでも低ければ見送る」で始める。**

実験26で、1問だけ confidence が 0.270 に落ちるケースがあった。
平均を取るとこれが埋もれる。自動投資で迷いのあるものを通す理由もない。

**厳しすぎて通るデータがなければ、「重みの大きいものだけ見る」に緩める。**
緩く始めて後から締めるより、厳しく始めて緩めるほうが安全。
緩く始めると、通ったものが本当に良かったのか分からなくなる。

### 閾値について

- **質問ごとに別の変数として持つ。** 全部同じ定数にしない。
  実験6は 0.5 付近、実験7は 0.3〜0.4 と、質問ごとに分かれ目が違った。
- **値は仮。** フェーズ4で confidence と精度を突き合わせて決める。
- **値の分布から 0.05 以上離す。** 実験25で、ぶれが ±0.02〜±0.03 あることが分かった。
  境目付近だと実行のたびに判定が変わる。
- **continuingの閾値は1にならない可能性**
  続くかどうかが未来の予測のため

## コード側の規律（Jev の判断を囲む）

ユーザー自身のトレードのルール。Jev が「良い」と言っても、ここで弾けば通さない。

- 5分足で5日線が25・75日線を追い越したときにエントリー
- 5日線が25日線の上（上昇傾向）のときしかエントリーしない
- 9時〜9時半の荒れやすい時間帯は特別扱い（確実に勝てる取引だけ、勝ったらすぐ引く）
- 上限値を決めておき、超えたら強制終了
- 持ち越さない
- 上がったらすぐ売らず逆指値で粘る。売れないことがないよう、板の厚いところの下に指値
- S高に張り付いたものは狙わない（前日S高で翌日入るのはあり）
- 出来高が少ないものは狙わない
- 買いが約定したらすぐ逆指値を入れる（どこで売るかを買うときに決めておく）
- 前日S高・出来高急増・値上がりランキングから翌日の候補を探す

これらはすべて数値で判定できるので、**コード側**。Jev には聞かない。

## その他の決定

- **`magnitude` は常に Jev に聞く。**
  文章に「営業利益30%増」と数字があればコードで判定できるが、
  表記のゆれ（30%、3割、1.3倍）への対応が要る。
  フェーズ3では縦切りを通すのが目的なので、切り分けは後回し。
- **確信が低いときは見送る。**（未決の論点2を解消）
  画面に出す・出さないは表示の話なので、フェーズ3で決める。

## なぜこの形になったか（経緯）

フェーズ2の冒頭で時間軸を決める際、いくつか方向転換した。記録として残す。

1. **当初は「1銘柄を買うか」を判断する想定だった。**
2. **短期（スキャルピング）寄りで検討した。**
   ユーザー自身がその時間軸でトレードしていること、
   中長期だと結果が出るまでに他の要因が混ざり検証しにくいことが理由。
3. **しかしスキャルピングだと Jev の出番がないと分かった。**
   判断材料が板・歩み値・価格の動きで、すべて数値。
   フェーズ1で「数値はコードのほうが確実」と確認済み。
4. **ニュースが出た直後に限定する案に移った。**
   しかし**普段のトレードでニュースが出る場面のほうが少ない**ことに気づいた。
5. **対象を市場全体に広げることで解決した。**
   1銘柄を見続けるのではなく、市場全体を監視して材料が出た銘柄を拾う。
   東証だけで数千銘柄あるので、1日に何十件も材料が出る。
   **Jev の速さが本当に効く場面**になる。1銘柄なら人が読めばいいが、数千銘柄は無理。
6. **ユーザーのトレード手法には文章を読む場面がないと分かった。**
   チャートの形と板と規律で完結している。
   前日の値上がりランキングから翌日を探すときも、上がった理由は調べていない。
   よってこのアプリは**ユーザーのやり方の延長ではなく、Jev の特性に合わせた別の設計**になる。
   ただしユーザーの規律は、判断の後の執行部分にそのまま活きる。
